## 1. 概述

**项目目标**：构建一个基于规则引擎的 Word 文档结构识别工具，将 .docx 文件解析为带层级关系和元数据的 JSON 结构树，支撑上层文档分析、信息抽取等应用场景。

### 2.1 文档解析层

#### (1) 文档加载器 (DocumentLoader)

| 项目 | 内容 |
|------|------|
| **职责** | 接收 .docx 文件路径，校验文件有效性，加载文档到内存，提供统一的文档对象访问接口 |
| **输入** | .docx 文件路径 |
| **输出** | 内部统一的 Document 对象 |
| **关键能力** | 文件格式校验、损坏检测、大文件流式加载、编码检测 |

#### (2) 样式分析器 (StyleAnalyzer)

| 项目 | 内容 |
|------|------|
| **职责** | 读取 Word 文档中所有段落的样式信息（样式名称、字体、字号、加粗、颜色、缩进、行距等），建立样式索引 |
| **输入** | Document 对象 |
| **输出** | 样式索引表 (StyleIndex)：段落 ID → 样式特征向量 |
| **关键能力** | 内置样式 + 自定义样式解析、样式继承链解析、中文字体/英文字体区分 |

#### (3) XML 解析器 (XmlParser)

| 项目 | 内容 |
|------|------|
| **职责** | 直接访问 docx 的 XML 底层 (word/document.xml)，获取 python-docx 未暴露的元信息（如分页符、分节符、批注、脚注尾注的引用标记等） |
| **输入** | Document 对象（底层 zip 包） |
| **输出** | 补充元素列表（分页符、批注引用、脚注引用等） |
| **关键能力** | XPath 查询、XML 命名空间处理、与 python-docx 对象模型的映射 |

### 2.2 规则引擎层

#### (4) 规则仓库 (RuleRepository)

| 项目 | 内容 |
|------|------|
| **职责** | 管理规则集（规则组），支持规则的加载、保存、增删改查。规则以 JSON/YAML 文件形式存储在本地 |
| **输入** | 规则文件路径 / 规则集名称 |
| **输出** | 规则集对象 (RuleSet) |
| **关键能力** | 多规则集管理（可为不同类型文档准备不同规则集）、规则优先级排序、规则冲突检测 |

#### (5) 规则解析器 (RuleParser)

| 项目 | 内容 |
|------|------|
| **职责** | 将规则定义文件（JSON/YAML）解析为内存中的规则对象，校验规则语法的合法性 |
| **输入** | 原始规则定义（字典形式或文件路径） |
| **输出** | Rule 对象列表 |
| **关键能力** | 规则语法校验、条件表达式解析、规则版本兼容性检查 |

#### (6) 规则执行器 (RuleEngine)

| 项目 | 内容 |
|------|------|
| **职责** | 接收段落/元素及其样式特征，遍历规则集进行匹配，返回分类结果。规则引擎是系统的核心决策组件 |
| **输入** | 样式特征向量 (StyleFeature) + 规则集 (RuleSet) |
| **输出** | 分类结果 (ClassificationResult)：元素类型 + 置信度 + 匹配的规则 ID |
| **关键能力** | 顺序匹配（优先级排序）、首匹配/最佳匹配策略、规则条件组合（AND/OR/NOT）、缺失特征降级处理 |

### 2.3 核心处理层

#### (7) 内容提取器 (ContentExtractor)

| 项目 | 内容 |
|------|------|
| **职责** | 根据分类结果，提取各类元素的具体内容。不同类型提取逻辑不同（表格提取行列数据、图片提取尺寸/路径、列表提取层级/序号等） |
| **输入** | 分类结果 + 原始元素句柄 |
| **输出** | 结构化内容字典 |
| **关键能力** | 图片提取（内嵌图片 + 绘制对象）、表格合并单元格处理、列表多层级解析、代码块保持缩进和换行 |

#### (8) 层级构建器 (HierarchyBuilder)

| 项目 | 内容 |
|------|------|
| **职责** | 将扁平的元素列表按标题层级构建为嵌套的 JSON 树结构。处理章节嵌套、多级标题、无标题段落归属等问题 |
| **输入** | 元素列表 (List[DocumentElement]) |
| **输出** | 嵌套的结构树 (StructureTree) |
| **关键能力** | 标题级别驱动的树构建、目录项特殊处理、正文段落归属到最近标题、跨章节元素（页眉页脚）的独立分支处理 |

#### (9) 元数据提取器 (MetadataExtractor)

| 项目 | 内容 |
|------|------|
| **职责** | 提取文档级和元素级的元数据：页码、位置坐标（相对段落顺序）、创建时间、作者等 |
| **输入** | Document 对象 + 元素列表 |
| **输出** | 元数据字典（文档级 + 元素级） |
| **关键能力** | 分页信息估算（按行距/字号推算）、页面设置读取、文档属性读取 |

#### (10) 分类器引擎 (ClassifierEngine)

| 项目 | 内容 |
|------|------|
| **职责** | 编排整个识别流程：对每个段落/元素，依次调用样式分析 → 规则匹配 → 内容提取 → 后处理纠偏 |
| **输入** | 原始 Document 对象 |
| **输出** | 已分类的元素列表 |
| **关键能力** | 多阶段分类（粗分类 → 细分类 → 上下文矫正）、上下文矫正（如连续相同样式的段落合并为一个正文块）、后处理规则（正则修正） |

### 2.4 交付层

#### (11) Python SDK (DocumentStructureSDK)

| 项目 | 内容 |
|------|------|
| **职责** | 面向开发者的 Python API，封装核心识别流程，提供便捷的调用接口 |
| **输入** | .docx 文件路径（或文件对象）+ 可选参数（规则集名称、输出格式选项等） |
| **输出** | StructureTree 对象（可序列化为 JSON） |
| **主要方法** | `recognize(filepath, ruleset=None, options=None) → StructureTree` |

#### (12) CLI 工具 (doc-struct)

| 项目 | 内容 |
|------|------|
| **职责** | 命令行入口，封装 SDK 调用，支持文件输入/输出重定向 |
| **输入** | 命令行参数 |
| **输出** | JSON 到 stdout 或文件 |
| **命令示例** | `doc-struct input.docx -o output.json` `doc-struct input.docx --ruleset academic` |

## 3. 接口定义

### 3.1 模块间内部接口

#### 接口 I1：文档加载 → 样式分析 / XML 解析

```
DocumentLoader.load(path: str) → docx.Document
```

#### 接口 I2：样式分析 → 分类器引擎

```
StyleAnalyzer.analyze(document: docx.Document) → StyleIndex
StyleIndex = Dict[str, StyleFeature]

StyleFeature = {
    "style_name": str,           # Word 样式名称（如 "Heading 1", "Normal"）
    "font_name": str,            # 字体名称
    "font_size": float,          # 字号（磅）
    "is_bold": bool,
    "is_italic": bool,
    "color_hex": Optional[str],  # 颜色十六进制
    "alignment": Optional[str],  # 对齐方式
    "indent_left": float,        # 左缩进（磅）
    "indent_first_line": float,  # 首行缩进
    "line_spacing": float,       # 行距倍数
    "space_before": float,       # 段前间距
    "space_after": float,        # 段后间距
    "outline_level": Optional[int],  # 大纲级别
    "list_format": Optional[str],    # 列表格式信息
}
```

#### 接口 I3：规则仓库 → 规则执行器

```
RuleRepository.load(ruleset_name: str) → RuleSet
RuleRepository.list_rulesets() → List[str]
RuleRepository.save(ruleset: RuleSet) → None

RuleSet = {
    "name": str,
    "version": str,
    "description": str,
    "rules": List[Rule],
    "metadata": dict,
}

Rule = {
    "id": str,
    "priority": int,
    "element_type": str,         # 目标元素类型
    "conditions": List[Condition],
    "match_strategy": str,       # "all" | "any"
    "confidence": float,         # 匹配时的默认置信度 (0-1)
    "description": str,
}

Condition = {
    "field": str,                # StyleFeature 中的字段名
    "operator": str,             # "eq" | "neq" | "gt" | "gte" | "lt" | "lte" | "contains" | "regex" | "in"
    "value": Any,
}
```

#### 接口 I4：规则执行器 → 分类器引擎

```
RuleEngine.classify(feature: StyleFeature, ruleset: RuleSet) → ClassificationResult

ClassificationResult = {
    "element_type": str,         # 见数据模型章节
    "confidence": float,         # 0.0 - 1.0
    "matched_rule_id": Optional[str],
    "matched_conditions": List[str],
    "fallback": bool,            # 是否走默认分类
}
```

#### 接口 I5：分类器引擎 → 内容提取器

```
ContentExtractor.extract(element_type: str, paragraph: Paragraph, document: docx.Document) → ElementContent
ContentExtractor.extract_table(table: Table) → ElementContent

ElementContent = {
    "text": Optional[str],              # 纯文本内容
    "rich_text": Optional[List[Run]],   # 富文本（保留格式）
    "table_data": Optional[TableData],  # 表格专用
    "image_data": Optional[ImageData],  # 图片专用
    "list_items": Optional[ListItems],  # 列表专用
}
```

#### 接口 I6：→ 层级构建器

```
HierarchyBuilder.build(elements: List[DocumentElement], metadata: DocumentMeta) → StructureTree
```

#### 接口 I7：SDK 顶层接口

```python
# docstruct/__init__.py

class DocStructSDK:
    def __init__(self, ruleset_path: Optional[str] = None):
        """
        初始化 SDK
        :param ruleset_path: 自定义规则集路径（可选，默认使用内置规则集）
        """

    def recognize(
        self,
        filepath: Union[str, Path],
        output_format: Literal["structure_tree", "flat_list"] = "structure_tree",
        include_metadata: bool = True,
        include_style_features: bool = False,
    ) -> StructureTree:
        """
        识别文档结构
        :param filepath: .docx 文件路径
        :param output_format: 输出格式
        :param include_metadata: 是否包含元数据
        :param include_style_features: 是否在输出中包含样式特征（调试用）
        :return: StructureTree 对象
        """

    def recognize_to_json(
        self,
        filepath: Union[str, Path],
        output_file: Optional[Union[str, Path]] = None,
        **kwargs,
    ) -> str:
        """
        识别文档结构并输出 JSON 字符串
        :param output_file: 输出文件路径（可选，不传则返回 JSON 字符串）
        :return: JSON 字符串（当 output_file 为 None 时）
        """
```

## 4. 数据模型

### 4.1 核心数据结构

#### DocumentElement（文档元素）

```
DocumentElement = {
    "id": str,                          # 唯一标识符（如 "elem_0001"）
    "type": ElementType,                # 元素类型枚举
    "level": Optional[int],             # 层级（标题级别/列表嵌套层级）
    "content": ElementContent,          # 内容
    "metadata": ElementMetadata,        # 元数据
    "children": List[DocumentElement],  # 子元素（嵌套结构）
    "confidence": float,                # 识别置信度
}
```

#### ElementType（元素类型枚举）

```
ElementType = {
    "document",          # 文档根节点
    "heading",           # 标题（level 区分级别）
    "paragraph",         # 正文段落
    "table",             # 表格
    "image",             # 图片
    "list_ordered",      # 有序列表
    "list_unordered",    # 无序列表
    "code_block",        # 代码块
    "block_quote",       # 引用/批注
    "header",            # 页眉
    "footer",            # 页脚
    "footnote",          # 脚注
    "endnote",           # 尾注
    "toc",               # 目录
    "toc_item",          # 目录项
    "page_break",        # 分页符
    "section_break",     # 分节符
    "comment",           # 批注
    "caption",           # 标题说明（图/表标题）
}
```

#### StructureTree（输出结构树）

```
StructureTree = {
    "version": str,                    # 识别引擎版本
    "generated_at": str,               # 生成时间（ISO 8601）
    "source_file": str,                # 源文件名
    "document_meta": DocumentMeta,     # 文档级元数据
    "root": DocumentElement,           # 根节点（type: "document"）
    "flat_index": Dict[str, str],      # 元素 ID → 类型 的平铺索引（快速查找）
}
```

#### DocumentMeta（文档级元数据）

```
DocumentMeta = {
    "page_count": Optional[int],       # 估算页数
    "paragraph_count": int,
    "table_count": int,
    "image_count": int,
    "author": Optional[str],
    "created_time": Optional[str],
    "modified_time": Optional[str],
    "title": Optional[str],
    "word_count": int,
    "language": Optional[str],
}
```

#### ElementMetadata（元素级元数据）

```
ElementMetadata = {
    "position": {                      # 在文档中的位置
        "index": int,                  # 全局段落序号（0-based）
        "page_estimate": Optional[int],# 估算页码
    },
    "style_name": Optional[str],       # Word 样式名称
    "style_features": Optional[dict],  # 样式特征向量（debug 模式下包含）
    "formatting": {                    # 格式信息
        "alignment": Optional[str],
        "indent": Optional[dict],
        "line_spacing": Optional[float],
    },
    "source": str,                     # 来源（"body" | "header" | "footer" | "footnote" | etc.）
}
```

### 4.2 规则配置数据模型

规则以 YAML 格式存储，易于手工编辑。示例如下：

```yaml
# rulesets/default.yaml
name: default
version: "1.0"
description: 通用文档结构识别规则集

rules:
  - id: heading_1
    priority: 100
    element_type: heading
    level: 1
    description: "样式名称为 Heading 1 或大纲级别为 1"
    match_strategy: any
    conditions:
      - field: style_name
        operator: eq
        value: "heading 1"
      - field: outline_level
        operator: eq
        value: 1
    confidence: 0.95

  - id: heading_2
    priority: 99
    element_type: heading
    level: 2
    description: "样式名称为 Heading 2 或大纲级别为 2"
    match_strategy: any
    conditions:
      - field: style_name
        operator: eq
        value: "heading 2"
      - field: outline_level
        operator: eq
        value: 2
    confidence: 0.95

  - id: heading_by_font
    priority: 50
    element_type: heading
    level: 0  # 由程序自动推断级别
    description: "字号 >= 14 且加粗的短文本，可能为标题"
    match_strategy: all
    conditions:
      - field: font_size
        operator: gte
        value: 14
      - field: is_bold
        operator: eq
        value: true
    confidence: 0.6

  - id: code_block
    priority: 60
    element_type: code_block
    description: "使用等宽字体（如 Courier New, Consolas）的段落"
    match_strategy: all
    conditions:
      - field: font_name
        operator: in
        value: ["Courier New", "Consolas", "Source Code Pro", "JetBrains Mono", "Fira Code"]
    confidence: 0.7

  - id: image_caption
    priority: 70
    element_type: caption
    description: "包含"图"或"Figure"开头的段落，通常为图片标题"
    match_strategy: all
    conditions:
      - field: text_content
        operator: regex
        value: "^(图|Figure|FIG)\\s*\\d+"
    confidence: 0.85

## 5. 技术选型

### 5.1 推荐技术栈

| 层次 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| 语言 | Python | 3.10+ | 生态丰富、文档处理库成熟、团队熟悉度 |
| 核心解析 | python-docx | 0.8.11+ | 最成熟的 .docx 解析库，支持段落/表格/图片/样式读取 |
| XML 解析 | lxml | 4.9+ | 高性能 XML 解析，完整 XPath 支持，适合底层 XML 操作 |
| 规则配置 | PyYAML + JSONSchema | 6.0+ | YAML 可读性强适合手工配置，JSON Schema 做规则校验 |
| CLI 框架 | click | 8.1+ | 轻量、声明式 CLI 参数定义，自动生成帮助文档 |
| 数据模型 | Pydantic | 2.0+ | 类型安全的数据模型定义，序列化/反序列化开箱即用 |
| 测试 | pytest | 7.4+ | 成熟的 Python 测试框架，参数化测试支持 |
| 包管理 | poetry | 1.7+ | 依赖管理 + 打包发布一体化 |
| 代码质量 | ruff | — | 极速的 lint + format 工具 |

### 5.2 技术选型说明

**关于 python-docx 的定位**：python-docx 支持读取段落、表格、图片、样式信息，但存在以下局限：
- 不直接提供分页符/分节符检测 → 由 XML 解析器 (lxml) 补充
- 图片提取仅支持内嵌图片 → 需要同时处理 DrawingML 对象
- 列表信息获取不完整 → 需结合 XML 层面解析 `w:numPr` 元素

**关于 Python 3.10+ 的理由**：使用 `match` 语句进行元素类型分发，使用 `Union[str, Path]` 等类型注解，为后续类型安全提供保障。

**关于 Pydantic 的选择**：输出 JSON 结构的序列化/校验用 Pydantic 实现更为安全可靠；同时在 SDK API 返回对象时可提供 IDE 自动补全。

## 6. 约束与风险

### 6.1 已知限制

| 限制项 | 说明 |
|--------|------|
| 仅支持 .docx 格式 | 不支持 .doc（旧版 Word 格式）和扫描 PDF。.doc 需通过 Word 或 LibreOffice 转换 |
| 不支持扫描件 | .docx 中的嵌入式扫描图片无法提取文字结构（需 OCR 引擎配合，不在当前范围） |
| 分页估算非精确 | Word 的分页取决于打印机驱动和渲染引擎，无法 100% 精确还原分页 |
| 表格复杂度受限 | 合并单元格复杂度过高的表格（跨行跨列组合），解析可能不完整 |
| 页眉页脚识别受限 | 只识别每节首页的页眉页脚，不同节的不同页眉页脚需要额外处理 |

### 6.2 潜在风险与应对方案

| 风险 | 概率 | 影响 | 应对方案 |
|------|------|------|----------|
| 中文文档样式不规范 | 高 | 中 | 规则引擎提供补丁机制，可为不规范文档单独配置规则；兜底规则保证至少识别为"正文" |
| 自定义样式覆盖官方样式 | 中 | 高 | 优先识别官方样式名称（Heading 1/2/3），再按字体特征启发式匹配，最终给出置信度 |
| 大文档（100页+）性能 | 中 | 低 | 单文档处理、无严格时间要求，性能不影响功能；后续可考虑增量解析优化 |
| 不同语言版本的 Word 样式名不同 | 中 | 中 | 规则集中包含样式名别名映射（如中文版 Word 使用"标题 1"而非"Heading 1"） |
| 规则配置错误导致误识别 | 低 | 高 | 规则校验机制（JSON Schema 校验 + 规则自检）；规则集版本管理，可回滚 |

### 6.3 性能预期

| 指标 | 预期值 | 说明 |
|------|--------|------|
| 单文档处理时间 | 1-5 秒 | 50-100 页普通文档（无大量图片） |
| 内存占用 | 50-200 MB | 取决于文档嵌入图片数量和尺寸 |
| JSON 输出大小 | 0.5-5 MB | 取决于文档内容和图片元数据量 |

## 8. 解析结果的保存与复用（MySQL 存储方案）

### 8.1 设计目标

1. **持久化存储**：将解析结果（StructureTree JSON）系统化保存到 MySQL，支持历史版本追溯
2. **关联模板**：每条解析记录关联 template_config.id，按模板维度管理解析结果
3. **规则优化反馈**：收集解析结果的统计信息，为规则引擎的调优提供数据支撑
4. **结果对比与版本追踪**：支持同一文档不同版本、不同规则集的解析结果差异对比
5. **查询接口**：提供 REST API 供前端和外部系统按条件检索解析结果

### 8.2 存储方案选型

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 本地 JSON 文件 | 简单直接 | 无查询能力、无版本管理 | 不适用 |
| SQLite | Python 内置 | 需要独立管理、与 Java 后端集成困难 | 不适用 |
| **MySQL（选型）** | 与 Template 项目一致、Java 生态成熟、支持并发 | 需要部署服务（已有） | **采用** |
| 本地文件 + API | 灵活 | 数据一致性难保障 | 不适用 |

**结论**：采用 **MySQL** 作为存储引擎，复用在 Template 项目中已有的 MySQL 数据库连接和 MyBatis-Plus 配置。新建 parse_record、parse_element、parse_diff_report 三张表。

    CONSTRAINT fk_diff_b FOREIGN KEY (record_id_b) REFERENCES parse_record(id) ON DELETE CASCADE
);
```

### 8.4 架构分层与数据流

v1.2 架构的重大变化是**将存储层从 Python 端迁移至 Java 端**，Python doc-struct 引擎专注解析，Java Template 后端负责存储与展示。

```
+------------------------------------------------------+
|              Python doc-struct 引擎                    |
|  +----------+    +----------+    +---------------+   |
|  | 解析引擎   |--->| 层级构建  |--->| StructureTree |   |
|  +----------+    +----------+    |   (JSON)      |   |
|                                  +-------+-------+   |
+------------------------------------------+-----------+
                                           |
                           CLI --save URL   |   子进程调用
                                           |
                                           v
+------------------------------------------------------+
|            Template 项目（Java Spring Boot）            |
|  +--------------------+    +----------------------+   |
|  | ParseRecordService |--->| MySQL 数据库          |   |
|  | (接收、存储、查询)  |    | parse_record          |   |
|  +--------+-----------+    | parse_element         |   |
|           |                | parse_diff_report     |   |
|  +--------+-----------+    +----------------------+   |
|  | ParseDiffService   |                               |
|  | (差异对比引擎)      |                               |
|  +--------------------+                               |
+------------------------------------------------------+
```

**数据流向说明**：

1. **解析生成**：Python doc-struct 引擎处理 .docx 文件，输出 StructureTree JSON
2. **数据传输**：两种方式：
   - CLI 模式：doc-struct input.docx --save http://localhost:8080/api/parse-record
   - 后端调用：Template 后端通过 ProcessBuilder 或 HTTP 调用 Python 脚本，获取 stdout 中的 JSON
3. **存储入库**：Template 后端 ParseRecordService 接收 JSON，存入 MySQL
4. **查询展示**：前端通过 REST API 查询 ParseRecordController 获取记录列表和详情
5. **差异对比**：ParseDiffService（Java 端实现）接收两个 structure_tree JSON，解析后进行逐元素对比

### 8.5 缓存策略

#### 缓存键设计

缓存键由三个要素组合而成，确保唯一性：

```
cache_key = SHA256( source_file_checksum + "|" + ruleset_name + "|" + ruleset_version )
```

- source_file_checksum：源文档内容的 SHA256 哈希
- ruleset_name：使用的规则集名称
- ruleset_version：规则集的版本号

只要任一要素变化，缓存自动失效。

#### 缓存生命周期

```
        文件首次解析               文件修改后重新解析
   +--------------------+       +--------------------+
   |  解析文档           |       |  解析文档           |
   |  保存到 MySQL       |       |  保存新记录（保留旧  |
   |  checksum = A      |------|  记录作为历史版本）  |
   +--------+-----------+       +--------+-----------+
            |                            |
            v                            v
   +--------------------+       +--------------------+
   | 同一文件再次解析    |       | 缓存未命中          |
   | checksum 不变      |       | checksum=A->B       |
   | 直接返回缓存       |       | 返回新解析结果      |
   +--------------------+       +--------------------+
```

> **v1.2 变更**：缓存存储在 MySQL parse_record 表中，通过 source_checksum + ruleset_name + ruleset_version 联合查询判断命中。缓存查询逻辑由 ParseRecordService 提供 REST API，Python 端不再直接操作数据库。

### 8.6 各场景的复用机制

#### 场景一：缓存加速（通过 API）

```

1. 计算 input.docx 的 SHA256
2. POST 到 /api/parse-record/check-cache（携带 checksum + ruleset 信息）
3. 命中 -> 返回已有记录的 ID 和 StructureTree
4. 未命中 -> Python 正常解析 -> POST 到 /api/parse-record -> MySQL 存储 -> 返回结果

#### 场景二：规则优化反馈

```

1. 查询 parse_record 表中使用了指定规则集的记录
2. 遍历记录的 structure_tree JSON，提取每条规则的匹配统计
3. 聚合计算匹配次数、匹配文档数、平均置信度

## 11. 文件上传与Python引擎集成

### 11.1 集成方案概述

Python doc-struct 引擎**独立于 Template Java 项目**，通过 ProcessBuilder 子进程方式调用。关键设计决策：

> **Java 不写临时文件。Python 通过 REST API 自行获取文件内容和回存解析结果。**

Java 只传递 `fileId`，Python 引擎通过 API 从数据库获取 `.docx` 内容，解析完成后通过 API 存回 `parse_record` 表。

### 11.2 完整数据流

```
┌──────────────────────────────────────────────────────────────────┐
│  Step 1: 上传                                                     │
│  Frontend → POST /api/word/upload                                │
│  → WordParseService.upload() 存入 user_upload_file (BLOB)        │
│  → 返回 fileId, 状态: UPLOADED                                   │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 2: 解析 (用户点击"解析"按钮)                                 │
│  Frontend → POST /api/word/{id}/parse-v2                         │
│  → WordParseService.parseV2(fileId)                              │
│                                                                  │
│    Java 端只做一件事：启动 Python 子进程，传入 fileId               │
│    ┌───────────────────────────────────────────────────────┐    │
│    │ ProcessBuilder:                                       │    │
│    │   python -m docstruct                                 │    │
│    │     --file-id 123                                     │    │
│    │     --api-url http://localhost:8080                   │    │
│    │     --template-id 5                                   │    │
│    │     --ruleset academic                                │    │
│    └───────────────────────────────────────────────────────┘    │
│                                                                  │
│    Java 读取 stdout/stderr，等待进程完成                           │
│    → 返回解析结果摘要给前端                                        │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 3: Python 引擎自主完成解析+存储                              │
│                                                                  │
│  ① 通过 API 获取文件:                                             │
│     GET {apiUrl}/api/word/{fileId}/raw                           │
│     → 获取 .docx 字节流                                           │
│                                                                  │
│  ② 执行解析:                                                      │
│     DocumentLoader → StyleAnalyzer → RuleEngine                  │
│     → ContentExtractor → HierarchyBuilder                        │
│     → StructureTree (JSON)                                       │
│                                                                  │
│  ③ 通过 API 存回解析结果:                                         │
│     POST {apiUrl}/api/parse-record                               │
│     Body: { structureTree, templateId, fileId, ... }             │
│                                                                  │
│  ④ 输出 JSON 结果到 stdout (供 Java 读取)                          │
└──────────────────────────────────────────────────────────────────┘
```

**核心原则**：Python 引擎不直接访问 MySQL 数据库，所有数据交互通过 Java REST API 完成。数据库访问逻辑完全封装在 Java 端。

### 11.3 新增 API：原始文件内容接口

为支持 Python 引擎获取文件，在 `WordController` 中新增：

```
GET /api/word/{id}/raw

请求参数:
  无（通过路径传递 fileId）

响应:
  Content-Type: application/octet-stream
  Body: user_upload_file.original_content 的原始字节（即 .docx 文件）

错误:
  404 - 文件不存在
  400 - 文件内容为空
```

```java
@GetMapping("/{id}/raw")
public ResponseEntity<byte[]> getRawContent(@PathVariable Long id) {
    UploadFile uf = uploadFileMapper.selectById(id);
    if (uf == null) {
        return ResponseEntity.notFound().build();
    }
    if (uf.getOriginalContent() == null) {
        return ResponseEntity.badRequest().build();
    }
    return ResponseEntity.ok()
            .contentType(MediaType.APPLICATION_OCTET_STREAM)
            .header("Content-Disposition", "attachment; filename=\"" + 
                    URLEncoder.encode(uf.getOriginalName(), StandardCharsets.UTF_8) + "\"")
            .body(uf.getOriginalContent());
}
```

```

### 11.8 与现有解析流程的共存

| 解析方式 | 引擎 | 接口 | 状态值 |
|---------|------|------|--------|
| 现有 | Java RecognitionEngine（正则匹配） | `POST /api/word/{id}/parse` | `PARSED` |
| 新增 | Python doc-struct（规则引擎） | `POST /api/word/{id}/parse-v2` | `PARSED_V2` |

- 两个接口独立并行，互不影响
- 前端解析按钮可根据模板配置选择调用哪个引擎
- 两种解析的结果都可在"解析结果"页面统一查看

### 11.9 异常处理

| 异常场景 | 处理方式 |
|---------|---------|
| Python 进程启动失败 | `PARSE_FAILED` + 错误信息写入 `user_upload_file.error_message` |
| 解析超时（默认5分钟） | 强制终止进程 + `PARSE_FAILED` |
| Python 返回非0退出码 | 读取 stderr 作为错误信息 |
| API 获取文件失败（404/400） | Python 输出错误到 stdout，Java 解析后标记失败 |
| API 保存结果失败 | Python 输出错误到 stdout + stderr 详细信息 |
| 进程管道死锁 | stdout/stderr 异步读取线程（与 SmartMatchTaskService 一致） |

### 11.10 CLI 接口变更汇总

原计划中的 `--save URL` 选项不再需要——Python 引擎始终通过 `--file-id` + `--api-url` 自动完成文件获取和结果保存，无需 Java 写临时文件，也无需用户手动指定 `--save`。

### B. 识别流程伪代码

```
function recognize(filepath):
    document = DocumentLoader.load(filepath)
    features = StyleAnalyzer.analyze(document)
    supplement = XmlParser.parse(document)
    
    flat_elements = []
    
    // 阶段 1：段落分类
    for paragraph in document.paragraphs:
        feature = features[paragraph.id]
        result = RuleEngine.classify(feature, active_ruleset)
        content = ContentExtractor.extract(result.type, paragraph, document)
        
        flat_elements.append(DocumentElement(
            type=result.type,
            level=result.level,
            content=content,
            confidence=result.confidence,
        ))
    
    // 阶段 2：补充非段落元素（表格、图片、分页符等）
    for table in document.tables:
        flat_elements.append(extract_table_element(table))
    
    for elem in supplement:
        flat_elements.append(elem)
    
    // 阶段 3：上下文矫正
    corrected = ClassifierEngine.correct_context(flat_elements)
    
    // 阶段 4：构建层级树
    tree = HierarchyBuilder.build(corrected)
    
    // 阶段 5：附加元数据
    tree.metadata = MetadataExtractor.extract(document, corrected)
    
    return tree
```
