# 文件删除与引擎配置分页功能设计文档

## 1. 概述

本文档定义两个独立的功能模块：为 Word 文件管理模块新增**物理删除**能力，为引擎配置列表在现有排序逻辑基础上新增**分页**能力，以满足产品对文件管理完整性和引擎配置列表可用性的需求。

---

## 2. 模块划分

### 模块一：文件删除与校验

| 项目 | 内容 |
|------|------|
| **职责** | 提供文件物理删除 API，增强导出前置校验 |
| **核心逻辑** | DELETE 操作直接删除 `user_upload_file` 表记录（物理删除）；export 接口增加文件解析状态校验，确保仅已解析文件可导出 |
| **不包含** | 级联删除关联表、逻辑删除（is_deleted 标记）、批量删除 |

### 模块二：引擎配置分页

| 项目 | 内容 |
|------|------|
| **职责** | 将引擎配置列表接口改造为分页查询，保持现有排序规则 |
| **核心逻辑** | 在 `listEngineConfigs` 接口中增加 `page`/`size` 参数，返回 `Page<EngineConfigDTO>`，排序逻辑保持不变（按 matchType 优先级 + sortOrder 升序） |
| **不包含** | 搜索功能、筛选功能、排序顺序变更 |

---

## 3. 接口定义

### 3.1 模块一：文件删除

#### 3.1.1 删除文件

| 项目 | 值 |
|------|-----|
| **方法** | `DELETE` |
| **路径** | `/api/word/{id}` |
| **参数** | `id` — 文件 ID（路径变量，`Long` 类型） |
| **返回值** | `ApiResponse<Void>` — 通用成功响应 |
| **错误码** | `404` — 文件不存在；`500` — 服务端异常 |

**请求示例：**
```
DELETE /api/word/42
```

**成功响应：**
```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

**失败响应（404）：**
```json
{
  "code": 404,
  "message": "文件不存在",
  "data": null
}
```

#### 3.1.2 导出文件（增强校验）

| 项目 | 说明 |
|------|------|
| **现有路径** | `POST /api/word/{id}/export`（不变） |
| **变更内容** | 增加前置校验：仅当文件 `status` 为 `PARSED` / `ADJUSTED` / `EXPORTED` 时才允许导出 |
| **新增错误码** | `400` — 文件未解析，提示"文件尚未解析，请先执行解析操作" |

---

### 3.2 模块二：引擎配置分页

#### 3.2.1 分页查询引擎配置列表（修改现有接口）

| 项目 | 变更前 | 变更后 |
|------|--------|--------|
| **方法** | `GET` | 不变 |
| **路径** | `/api/template/{templateId}/engine-config/list` | 不变 |
| **参数** | 无分页参数 | `page`（默认 1）、`size`（默认 10） |
| **返回值** | `ApiResponse<List<EngineConfigDTO>>` | `ApiResponse<Page<EngineConfigDTO>>` |
| **排序** | Java 内存排序：matchType 优先级 + sortOrder | **保持不变** |

**请求示例：**
```
GET /api/template/5/engine-config/list?page=1&size=10
```

**成功响应：**
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "records": [ ... ],
    "total": 25,
    "size": 10,
    "current": 1,
    "pages": 3
  }
}
```

**排序规则（保持不变）：**
```
SPECIAL(0) < COVER(1) < TOC(2) < TITLE(3) < BODY(4) < 其他(5)
同级类型内按 sort_order ASC 升序
```

## 5. 改动范围

### 5.1 后端文件

#### 5.1.1 `WordController.java`

| 改动项 | 说明 |
|--------|------|
| **新增** `DELETE /api/word/{id}` | 注入 `WordParseService.delete(id)`，返回 `ApiResponse<Void>` |
| **修改** `export` 方法 | export 之前增加解析校验：若文件未经过解析，返回 `ApiResponse.fail(400, "文件尚未解析，请先执行解析操作")`，提升错误消息可读性 |

#### 5.1.2 `WordParseService.java`

| 改动项 | 说明 |
|--------|------|
| **新增** `delete(Long id)` 方法 | 业务逻辑：先 `selectById` 检查存在性（不存在则抛异常），再 `uploadFileMapper.deleteById(id)` 进行物理删除 |
| **修改** `export(Long fileId)` 方法 | 在获取文件后增加状态校验：仅当 `status` 为 `PARSED` / `ADJUSTED` / `EXPORTED` 时才放行，否则抛出 `RuntimeException("文件尚未解析，请先执行解析操作")` |

#### 5.1.3 `TemplateController.java`

| 改动项 | 说明 |
|--------|------|
| **修改** `listEngineConfigs` 方法 | 参数增加 `@RequestParam(defaultValue = "1") int page` 和 `@RequestParam(defaultValue = "10") int size`；返回值改为 `ApiResponse<Page<EngineConfigDTO>>`；调用 `templateService.listEngineConfigs(templateId, page, size)` |

#### 5.1.4 `TemplateService.java`

| 改动项 | 说明 |
|--------|------|
| **修改** `listEngineConfigs` 方法签名 | 由 `listEngineConfigs(Long templateId)` 改为 `listEngineConfigs(Long templateId, int page, int size)`，返回类型由 `List<EngineConfigDTO>` 改为 `Page<EngineConfigDTO>` |
| **修改** `listEngineConfigs` 方法实现 | 流程改为：①查询全部引擎配置 → ②批量填充规则名称 → ③按 matchType + sortOrder 排序 → ④手动计算分页偏移并构造 `Page<EngineConfigDTO>` 返回。保持现有排序逻辑完全不变 |

> **分页实现说明**：由于排序规则是基于 `matchType` 枚举值的自定义优先级（非简单列排序），无法直接通过 MyBatis Plus 的 `ORDER BY` 实现正确分页。因此采用"全量查询 → 内存排序 → 内存分页"的策略。每模板的引擎配置数量通常不超过数百条，此策略对性能影响可忽略。

#### 5.2.3 `src/views/file/FileUpload.vue`

| 改动项 | 说明 |

| **新增** `handleDelete` 方法 | 调用 `ElMessageBox.confirm` 二次确认后调用 `deleteFile` API，成功时显示 `ElMessage.success('删除成功')`，并刷新列表 |

#### 5.2.4 `src/views/template/EngineConfig.vue`

| 改动项 | 说明 |
|--------|------|
| **新增** 分页状态变量 | 添加 `currentPage`（默认 1）、`pageSize`（默认 10）、`total`（默认 0）三个响应式变量 |
| **修改** `loadConfigList` 方法 | 调用 `getEngineConfigList` 时传入 `{ page: currentPage.value, size: pageSize.value }`；响应用于更新 `configList`（从 `res.records`）、`total`（从 `res.total`） |
| **修改** `onTemplateChange` 方法 | 切换模板时重置 `currentPage` 为 1 |
| **新增** 分页组件 | 在 `el-table` 下方新增 `<el-pagination>` 组件，绑定 `currentPage`/`pageSize`/`total`，监听 `current-change` 和 `size-change` 事件刷新列表 |
| **修改** `openCreateDialog` / `openEditDialog` 方法 | 新增/编辑成功后需重置到第一页并刷新（保持用户体验一致性） |
| **删除确认** | 当前已使用 `ElMessageBox.confirm` + `ElMessage.success`，保持不变 |

> **分页交互说明**：用户切换模板时自动回到第一页；切换每页条数时重置到第一页；新增/编辑/删除操作后刷新当前页列表。

## 6. 约束与风险

### 6.1 已知限制

| 限制项 | 说明 | 应对方案 |
|--------|------|----------|
| **引擎配置分页为内存分页** | 由于自定义排序无法通过 SQL `ORDER BY` 实现，采用全量查询后内存分页 | 每模板引擎配置通常不超过数百条，性能可接受；如未来数据量增长，可考虑在 `EngineConfig` 表增加 `sort_priority` 计算列 |
| **物理删除不可恢复** | 删除操作直接从数据库移除记录 | 前端通过 `ElMessageBox.confirm` 二次确认降低误操作概率；建议未来在运营后台增加审计日志 |
| **单一文件删除** | 当前接口仅支持按 ID 单条删除 | 如未来需要批量删除，可新增 `POST /api/word/batch-delete` 接口接收 ID 列表 |
| **文件删除不处理关联数据** | 不涉及其他表的级联操作 | 当前业务模型中上传文件与其他表无外键依赖；仅删除 `user_upload_file` 自身记录 |

### 6.2 兼容性

- 引擎配置分页接口的返回值**不向前兼容**——前端需要同步改造 `getEngineConfigList` 的调用方。
- 文件删除是新接口，不存在兼容性问题。
- export 接口的增强校验行为变更：原有调用方若在文件未解析时调用，之前可能返回 `500` 并附带 XML 解析异常堆栈，变更为返回清晰的 `400` 错误消息。属于**改善**，不破坏合理业务场景。

### 6.3 安全注意事项

- DELETE 接口当前未引入鉴权拦截（与项目现有风格一致）。如后续接入登录体系，需在 Controller 层补充权限校验。
- delete 操作返回 `ApiResponse<Void>`，不返回删除的数据详情，避免信息泄露。

## 附录：主要设计决策

以下是用户确认的五项决策的落地方案对照：

| # | 决策项 | 确认方案 | 实现方式 |
|---|--------|----------|----------|
| 1 | 删除方式 | 物理删除 | `uploadFileMapper.deleteById(id)` 直接 DELETE |
| 2 | 关联删除 | 仅删记录本身 | 不涉及其他表，无级联逻辑 |
| 3 | 引擎配置分页 | 仅分页 + 保持排序 | 内存排序后手动分页，不增加搜索/筛选 |
| 4 | 前端提示 | ElMessage 顶部消息通知 | 保持现有 `ElMessage.success` / `ElMessage.error` 模式 |
| 5 | 删除接口返回 | `ApiResponse<Void>` | `return ApiResponse.ok(null)` |
