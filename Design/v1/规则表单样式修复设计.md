# 规则表单样式修复设计文档

## 1. 概述

### 1.1 背景

模板规则编辑对话框（TemplateDetail.vue）中的段落样式表单存在一系列问题，用户反馈如下：

1. **输入框变形，+/- 按钮失效** — `el-input-number` 组件渲染异常，导致界面不可用
2. **颜色字段** — 当前使用普通文本输入框，需替换为颜色选择器
3. **精度和单位** — 数值输入框缺少精度控制和单位显示
4. **NULL 值处理** — 无值字段被发送到后端，覆盖已有值

### 1.2 目标

- 修复 `el-input-number` 的布局异常，确保所有数值输入框可正常使用
- 替换颜色字段为 Element Plus 颜色选择器
- 为数值字段添加合适的 `step`/`precision` 属性和单位标签
- 前端不发送空值字段，防止后端 `BeanUtils.copyProperties` 覆盖已有数据

---

## 2. 问题根因分析

### 2.1 问题一：输入框变形，+/- 按钮失效（布局问题）

#### 根因 1A — 容器宽度严重不足（首要原因）

规则编辑对话框宽度 600px，其中段落设置的三列布局代码如下：

```html
<el-row :gutter="20">
  <el-col :span="8">  <!-- 首行缩进 -->
    <el-form-item label="首行缩进">
      <el-input-number v-model="ruleForm.textIndent" :min="0" style="width: 100%" />
    </el-form-item>
  </el-col>
  <el-col :span="8">  <!-- 行距 -->
    <el-form-item label="行距">
      <el-input-number v-model="ruleForm.lineSpacing" ... />
    </el-form-item>
  </el-col>
  <el-col :span="8">  <!-- 段前距 -->
    <el-form-item label="段前距">
      <el-input-number v-model="ruleForm.spaceBefore" ... />
    </el-form-item>
  </el-col>
</el-row>
```

宽度计算链（Element Plus 默认样式下）：

| 层级 | 宽度计算 | 结果 |
|------|----------|------|
| 对话框 body | `600px - 20px（padding）× 2` | ~560px |
| `el-row`（含 gutter 20px） | `560px - 20px 间距` | ~540px 可用 |
| `el-col :span="8"` | `540px × 8/24` | **~180px** |
| `el-form-item` 标签区 | `label-width="120px"`（继承自父级 `el-form`） | 120px |
| `el-input-number` 内容区 | `180px - 120px` | **~60px** |

Element Plus 默认的 `el-input-number`（带左右两侧 +- 按钮）需要约 150px 的最小宽度才能正常渲染。在仅 60px 的容器中，按钮被挤出可视区域，输入框变形。

这是 **"输入框变形，+-按钮失效"** 的核心根因。

#### 根因 1B — v-model 绑定 null 值（次要原因）

后端 `TemplateRuleDTO` 中 `textIndent`、`lineSpacing`、`spaceBefore`、`spaceAfter` 字段类型为 `BigDecimal`。当数据库对应列为 NULL 时，后端返回 JSON 中包含 `"textIndent": null`。

前端编辑规则时执行：
```javascript
ruleForm.textIndent = row.textIndent  // row.textIndent === null
```

此时 `el-input-number` 的 `v-model` 绑定值为 `null`。Element Plus 的 `el-input-number` 在 `v-model="null"` 时存在组件内部状态不一致的问题，可能表现为显示异常和按钮无响应。

**两者叠加效应**：容器过窄导致的渲染异常 + null 值导致的内部状态异常，共同造成了用户看到的"输入框变形，+-按钮失效"。

#### 根因 1C — font-size 和 spaceBefore 没有 `:step` 属性

`textIndent`、`spaceBefore`、`spaceAfter`、`fontSize` 四个 `el-input-number` 缺少 `:step` 属性，默认 step 为 1。虽然这不是导致变形的直接原因，但不一致的精度设置影响用户体验。

### 2.2 问题二：颜色字段使用文本输入

`fontColor` 和 `highlightColor` 字段当前使用 `<el-input>` 文本输入框，需要用户手动输入十六进制颜色值，易出错、体验差。

### 2.3 问题三：NULL 值覆盖（数据完整性问题）

前端 `handleSaveRule` 方法构造请求体时，所有字段均被包含：
```javascript
const data: TemplateRule = {
  name: ruleForm.name,
  fontSize: ruleForm.fontSize,     // null
  textIndent: ruleForm.textIndent, // null
  // ...
}
await updateRule(templateId, editingRuleId.value, data)
```

后端 `updateRule` 方法：
```java
BeanUtils.copyProperties(dto, rule, "id", "templateId");
```

当 DTO 中字段为 null 时，`BeanUtils.copyProperties` 会将 null 复制到实体对象上，覆盖数据库中已有的值。这意味着用户打开编辑对话框（不做任何修改）直接保存，就会导致所有 NULL 字段的数据被清空。

## 3. 解决方案

### 3.1 解决输入框变形（布局修复）

#### 方案：增大对话框宽度 + 调整列布局

**3.1.1 对话框宽度调整**

| 属性 | 当前值 | 目标值 | 原因 |
|------|--------|--------|------|
| `el-dialog` width | `600px` | `720px` | 为三列布局提供足够容器宽度 |

**3.1.2 段落字段布局重构**

当前布局（3列 span="8"）：

| 首行缩进 | 行距 | 段前距 |
|-----------|------|--------|
| ~180px | ~180px | ~180px |

修改为（2列 span="12" + 另起一行）：

| 首行缩进 (span="12") | 行距 (span="12") |
|----------------------|-------------------|
| **段前距 (span="12")** | **段后距 (span="12")** |

这一修改将每个 `el-input-number` 的可用内容区从 ~60px 提升至：

- 对话框 body：`720px - 40px = 680px`
- 每列：`(680 - 20) × 12/24 = 330px`
- 内容区：`330px - 120px（label） = 210px`

210px 对于 `el-input-number`（默认左右按钮布局）完全充足。

**3.1.3 添加 controls-position 属性**

在所有 `el-input-number` 上添加 `controls-position="right"`，将 +- 按钮统一放在右侧，进一步减少水平空间占用，且视觉上更紧凑统一。

| 属性 | 值 |
|------|-----|
| `controls-position` | `"right"` |

**3.1.4 字号字段宽度修复**

当前字号（fontSize）位于 `el-col :span="12"`，内容区约 150px，勉强可用。通过 `controls-position="right"` 即可保证正常渲染，无需额外布局调整。

### 3.2 颜色选择器替换

| 字段 | 当前组件 | 目标组件 | 属性 |
|------|----------|----------|------|
| 字体颜色 (`fontColor`) | `<el-input>` | `<el-color-picker>` | `show-alpha="false"` |
| 高亮颜色 (`highlightColor`) | `<el-input>` | `<el-color-picker>` | `show-alpha="false"` |

`show-alpha="false"` 确保只输出 `#RRGGBB` 格式（不含 alpha 通道），符合用户选择的方案 A。

当颜色值为空时，`el-color-picker` 的 `v-model` 应绑定 `null` 或 `undefined`，组件显示为空状态。

### 3.3 精度与单位

#### 3.3.1 step / precision 属性清单

| 表单标签 | 绑定字段 | step | precision | 数据类型 |
|----------|----------|------|-----------|----------|
| 字号(磅) | `fontSize` | `1` | `0` | 整数（磅值） |
| 首行缩进(字符) | `textIndent` | `0.1` | `1` | 小数（字符数） |
| 行距(倍) | `lineSpacing` | `0.1` | `1` | 小数（倍数） |
| 段前距(磅) | `spaceBefore` | `0.1` | `1` | 小数（磅值） |
| 段后距(磅) | `spaceAfter` | `0.1` | `1` | 小数（磅值） |

说明：`fontSize` 使用 `:step="1"`（不传时默认为 1），不设置 precision 即可。字号通常是整数磅值，无需小数。

#### 3.3.2 标签变更

| 当前标签 | 修改后标签 | 说明 |
|----------|-----------|------|
| 字号 | 字号(磅) | 新增单位 |
| 首行缩进 | 首行缩进(字符) | 新增单位 |
| 行距 | 行距(倍) | 新增单位 |
| 段前距 | 段前距(磅) | 新增单位 |
| 段后距 | 段后距(磅) | 新增单位 |
| 字体名称 | 字体名称 | 不变 |
| 字体颜色 | 字体颜色 | 不变 |
| 高亮颜色 | 高亮颜色 | 不变 |

### 3.4 NULL 值处理

#### 3.4.1 前端改造：条件性构建请求体

修改 `handleSaveRule` 方法，使用条件展开语法仅包含非空值字段：

```typescript
const data: Record<string, any> = {
  name: ruleForm.name,  // name 为必填字段，始终发送
}

// 仅在值非空时加入字段
if (ruleForm.fontName)            data.fontName = ruleForm.fontName
if (ruleForm.fontSize != null)    data.fontSize = ruleForm.fontSize
// ... 以此类推所有可选字段
```

这种方式确保：
- 必填字段（name）始终发送
- 可选字段仅在值不为 `null`/`undefined` 时发送
- 后端 `BeanUtils.copyProperties` 不会覆盖没有出现在 DTO 中的字段

#### 3.4.2 后端兼容性

后端无需修改。`BeanUtils.copyProperties` 默认仅复制源对象中非 null 的字段......等，这是错误的。`BeanUtils.copyProperties` 会复制 null 值。

实际上，后端 `updateRule` 方法：
```java
BeanUtils.copyProperties(dto, rule, "id", "templateId");
```

当前端不发送 null 字段时，DTO 中对应字段为 `null`（Java 对象默认值），`BeanUtils.copyProperties` 会将 null 复制到实体中。

**因此，后端也需要处理 null 值问题。**

#### 3.4.3 后端改造方案

**方案 A（推荐）：使用 Spring BeanUtils 的 copyProperties 忽略 null**

Spring 的 `BeanUtils.copyProperties` 方法（注意是 `org.springframework.beans.BeanUtils`，不是 Apache 的）有一个重载版本可以传入要忽略的属性名。但无法直接忽略 null。

改用 Apache Commons BeanUtils 或自行封装 Utility 方法。

**方案 B（推荐）：手动更新非空字段**

在 `TemplateService.updateRule` 中，仅当 DTO 字段非空时才 set 到实体：

```java
public TemplateRule updateRule(Long id, TemplateRuleDTO dto) {
    TemplateRule rule = templateRuleMapper.selectById(id);
    if (rule == null) {
        log.error("规则不存在: id={}", id);
        return null;
    }
    // 仅当 DTO 中字段非空时才更新
    if (dto.getName() != null) rule.setName(dto.getName());
    if (dto.getFontName() != null) rule.setFontName(dto.getFontName());
    if (dto.getFontSize() != null) rule.setFontSize(dto.getFontSize());
    // ... 以此类推
    templateRuleMapper.updateById(rule);
    return rule;
}
```

这种方式的优点是简单明确，缺点是字段较多时代码略显冗长。

**方案 C（推荐）：使用 BeanUtils.copyProperties 配合字段白名单**

目前的 `BeanUtils.copyProperties(dto, rule, "id", "templateId")` 已经忽略了 id 和 templateId。在此基础上，对每个可为 null 的字段在 DTO 上通过 `@JsonInclude(JsonInclude.Include.NON_NULL)` 注解控制序列化行为。但这只影响 JSON 序列化，不影响 `BeanUtils.copyProperties` 的行为。

**最终推荐：采用方案 B（手动判断），代码最清晰可维护。** 同时前端侧仍然按 3.4.1 的条件构建方式，双重保障。

> **决策理由**：虽然前端条件构建可以减少传输，但后端必须独立具备 null 值保护能力。手动 set 方式在字段数量可接受（约 15 个）的情况下是最可控的方案。

#### 4.1.2 `src/types/api.ts`（可选）

当前 `TemplateRule` 接口定义：
```typescript
export interface TemplateRule {
  textIndent?: number
  lineSpacing?: number
  // ...
}
```

`textIndent` 等字段定义为 `number` 类型，但后端 `BigDecimal` 类型在 JSON 序列化后可能是数字或 null。当前定义中字段为 `?: number`（可选），可以接受 `undefined` 但不接受 `null`。

建议将字段类型统一为 `?: number | null`，以反映后端可能返回 null 的事实。

不过这不是必须的改动——当前代码中直接赋值 `ruleForm.textIndent = row.textIndent` 在值 null 时能正常执行。但如果使用 TypeScript 严格模式，会遇到类型错误。

**决定：暂不修改 types/api.ts。** 当前项目未启用严格模式，直接赋值 null 到可选字段在运行时没有影响。将此作为可选优化项。

### 4.2 后端文件

#### 4.2.1 `src/main/java/com/template/service/TemplateService.java`

**`updateRule` 方法** — 从 `BeanUtils.copyProperties` 改为手动更新非空字段：

```java
@Transactional
public TemplateRule updateRule(Long id, TemplateRuleDTO dto) {
    TemplateRule rule = templateRuleMapper.selectById(id);
    if (rule == null) {
        log.error("规则不存在: id={}", id);
        return null;
    }
    // 仅当 DTO 字段非空时才更新，防止 null 覆盖已有值
    if (dto.getName() != null)            rule.setName(dto.getName());
    if (dto.getFontName() != null)        rule.setFontName(dto.getFontName());
    if (dto.getFontSize() != null)        rule.setFontSize(dto.getFontSize());
    if (dto.getFontBold() != null)        rule.setFontBold(dto.getFontBold());
    if (dto.getFontItalic() != null)      rule.setFontItalic(dto.getFontItalic());
    if (dto.getFontUnderline() != null)   rule.setFontUnderline(dto.getFontUnderline());
    if (dto.getFontStrike() != null)      rule.setFontStrike(dto.getFontStrike());
    if (dto.getFontColor() != null)       rule.setFontColor(dto.getFontColor());
    if (dto.getTextAlign() != null)       rule.setTextAlign(dto.getTextAlign());
    if (dto.getTextIndent() != null)      rule.setTextIndent(dto.getTextIndent());
    if (dto.getLineSpacing() != null)     rule.setLineSpacing(dto.getLineSpacing());
    if (dto.getSpaceBefore() != null)     rule.setSpaceBefore(dto.getSpaceBefore());
    if (dto.getSpaceAfter() != null)      rule.setSpaceAfter(dto.getSpaceAfter());
    if (dto.getHighlightColor() != null)  rule.setHighlightColor(dto.getHighlightColor());
    
    templateRuleMapper.updateById(rule);
    return rule;
}
```

> **关于 fontBold 等开关字段的特殊说明**：当前 DTO 中这些字段为 `Integer` 类型，值为 `0` 或 `1`。前端会始终发送这些字段（因为它们通过 `el-switch` 绑定，始终有值）。为了统一处理规则，仍然使用非空判断逻辑。如果用户选择的开关值为 0，仍会被发送和更新，这是正确的行为。

**注意事项**：
- 前端通过 `el-switch` 绑定的字段（fontBold, fontItalic, fontUnderline, fontStrike）始终有值（0 或 1），不存在 null 问题
- 前端通过 `el-input-number` 绑定的字段（fontSize, textIndent, lineSpacing, spaceBefore, spaceAfter）在未操作时可能为 null
- 前端通过 `el-color-picker` 绑定的字段（fontColor, highlightColor）在未选择时可能是空字符串

## 7. 约束与风险

### 7.1 兼容性

| 风险项 | 等级 | 说明 | 应对 |
|--------|------|------|------|
| 前端改造后需验证所有 el-input-number 的 v-model 绑定 | 中 | 属性配置变化（step、precision、controls-position）可能影响组件行为 | 实现后逐个字段验证：新增、编辑、清空后保存 |
| el-color-picker 的 v-model 类型 | 低 | 后端期望 `String` 类型（如 `"#FF0000"`），`el-color-picker` 输出也是 `String` | 无兼容问题 |
| 后端 `updateRule` 手动 set 字段 | 中 | 若有新字段加入 `TemplateRule` 但忘记在 `updateRule` 中添加对应的 set 调用 | 在 CLAUDE.md 或代码注释中标注该风险；可考虑未来统一使用字段白名单反射工具 |

### 7.2 已知约束

| 约束项 | 说明 |
|--------|------|
| **不允许用户清空字段为 NULL** | 由于前端不发送 null 字段，且后端仅更新非空字段，用户无法通过编辑对话框将某个字段从有值改为 NULL。如需此能力，需增加"清除"按钮或特殊标记。当前迭代暂不实现 |
| **el-color-picker 无 "清除" 按钮** | `el-color-picker` 默认不支持清除颜色值。用户选择了颜色后无法恢复为空。如需此能力，需通过自定义 `footer` 插槽添加重置按钮 |
| **backend null 保护只适用于 update** | `createRule` 方法仍使用 `BeanUtils.copyProperties(dto, rule)`，创建时 DTO 中的 null 字段在数据库中会变成 NULL，这是期望行为（新建时不需要写入默认值） |

### 7.3 测试要点

| 测试场景 | 预期结果 |
|----------|----------|
| 新增规则，所有数值字段留空 | 创建成功，数据库对应字段为 NULL |
| 编辑规则，不修改任何字段直接保存 | 所有字段值保持不变 |
| 编辑规则，修改其中几个字段 | 仅修改字段更新，其余不变 |
| 编辑规则，使用颜色选择器选择颜色 | 颜色值以 `#RRGGBB` 格式保存 |
| 编辑规则，操作 el-input-number 的 +/- 按钮 | 按钮正常响应，步长符合设置 |
| 编辑规则，el-input-number 为 null 时打开对话框 | 输入框显示为空，无异常渲染 |
| 不同分辨率下打开对话框 | 输入框在所有窗口尺寸下均正常显示 |

### 7.4 后续优化方向（不在本次范围）

- **字段清零能力**：为 `el-input-number` 添加 `clearable` 属性或独立"重置"按钮，允许用户将字段从有值改为 NULL
- **el-color-picker 空值重置**：通过 footer 插槽或自定义触发器支持清除颜色
- **统一工具类**：后端 `BeanUtils` 增强，支持"仅复制非 null 字段"模式，替代手动 set
- **TypeScript 类型增强**：`TemplateRule` 接口字段类型改为 `number | null`，以准确反映后端数据

## 附录：设计决策摘要

| # | 决策项 | 选择 | 理由 |
|---|--------|------|------|
| 1 | 对话框宽度 | 600px → **720px** | 为字段提供充足空间，避免过度挤压 |
| 2 | 段落字段布局 | 3列 → **2行×2列 (span="12")** | 每列 ~330px，内容区 ~210px，充分满足 el-input-number 需求 |
| 3 | 按钮位置 | **controls-position="right"** | 水平空间占用更小，视觉更统一 |
| 4 | 颜色选择器类型 | **el-color-picker, show-alpha=false** | 仅输出 #RRGGBB 格式，符合用户要求 |
| 5 | step/precision | 见 3.3.1 表格 | 按字段分别设定 |
| 6 | NULL 前端处理 | **条件构建请求体** | 不发送 null 字段 |
| 7 | NULL 后端处理 | **手动 set 非空字段** | 防止 BeanUtils.copyProperties 覆盖已有值 |
| 8 | createRule 方法 | **保持原样** | 新建时 null 值在数据库存 NULL 是期望行为 |
