# 段落调整面板搜索展示与性能优化设计文档

## 概述

本文档针对解析预览页（ParsePreview.vue）右侧"段落调整"面板的三个功能改进任务进行需求分析和方案设计。三个任务均发生在同一组件内的 .legend-panel 区域，代码改动都集中在 ParsePreview.vue 单个文件中。

---

## 任务1：搜索功能

### 1.1 需求分析

当前"段落调整"区域仅展示所有段落的平铺列表，当段落数量较多时，用户难以快速定位到特定的段落。需要在"段落调整"标题下方添加搜索功能。

#### 1.1.1 问题澄清

**问题1：搜索匹配逻辑采用什么策略？**

| 方案 | 描述 | 评价 |
|------|------|------|
| A（推荐） | 不区分大小写的子串包含匹配（toLowerCase + includes） | 最符合用户直觉，对中文搜索友好 |
| B | 区分大小写的精确匹配 | 对中文无意义，对英文过于严格 |
| C | 正则表达式匹配 | 用户不熟悉正则语法，过于复杂 |

推荐方案 A。同时需要对 para.text 做空值保护。

**问题2：多个匹配结果时的交互模式？**

| 方案 | 描述 | 评价 |
|------|------|------|
| A | 仅定位第一个匹配项 | 后续查看不便 |
| B（推荐） | 支持上/下翻导航，显示当前位置和总数（如 3/12） | 交互完整，适合批量检查 |
| C | 展开所有匹配项并全部高亮 | 同时展开多项可能导致性能问题 |

推荐方案 B。

**问题3：无匹配结果时如何提示？**

| 方案 | 描述 | 评价 |
|------|------|------|
| A | 使用 ElMessage.info 弹出 Toast 提示 | 一闪而过不够醒目 |
| B（推荐） | 在搜索框下方显示内联文字"无匹配结果" | 一直可见，不打扰用户 |
| C | 搜索框边框变红色 | 不符合常规交互模式 |

推荐方案 B。

**问题4：搜索框的 UI 位置和样式？**

搜索框放在"段落调整"标题与段落列表之间。宽度 100%，使用 Element Plus 的 el-input + el-button 组合，支持回车触发搜索。

布局示意：

```
段落调整（标题）
┌──────────────────┐
│ [搜索输入框] [搜索] │  ← 新增搜索栏
├──────────────────┤
│ 3/12  [上] [下]   │  ← 新增导航栏（有结果时显示）
├──────────────────┤
│ 段落列表...           │
└──────────────────┘
```

**问题5：是否高亮匹配文本？**

| 方案 | 描述 | 评价 |
|------|------|------|
| A（推荐） | 对匹配的文本片段用 span.search-highlight 高亮 | 视觉反馈直观 |
| B | 仅给段落项添加高亮边框 | 不够直观 |
| C | 不高亮，仅滚动定位 | 视觉反馈不足 |

推荐方案 A。使用 v-html 渲染，需先对文本做 HTML 转义以避免 XSS 风险。

### 1.2 技术方案

#### 1.2.1 新增响应式状态

```typescript
const searchKeyword = ref<string>('')
const searchResults = ref<number[]>([])        // 匹配段落的 v-for index
const currentSearchIdx = ref(0)                // 当前定位到第几个匹配
const hasSearched = ref(false)                 // 是否已执行过搜索
```

#### 1.2.2 搜索与导航函数

- performSearch(): 遍历 parseResult.paragraphs，对每项的 para.text 做 case-insensitive 包含匹配，结果存入 searchResults
- nextMatch(): currentSearchIdx 递增，循环到第一个
- prevMatch(): currentSearchIdx 递减，循环到最后一个
- scrollToMatch(idx): 展开对应段落 (expandedAdjustItems[paraIdx] = true)，await nextTick() 后执行 scrollIntoView({ behavior: 'smooth', block: 'center' })

#### 1.2.3 高亮文本渲染

新增 highlightText(text, keyword) 函数：查找 keyword 在 text 中的位置，替换为 <span class="search-highlight">keyword</span> 标签。使用 v-html 渲染前先通过自定义 escapeHtml() 对 text 进行转义。

#### 1.2.4 模板修改

在 h3.legend-title 和 div.adjust-section 之间插入搜索栏和导航栏。在 .adjust-item 上添加 data-index 属性和 is-match / is-current-match 动态 class，用于搜索定位和样式高亮。

### 1.3 改动范围

| 项目 | 内容 |
|------|------|
| template | 新增搜索栏、导航栏 HTML |
| script | 新增 ~8 个响应式状态和 ~6 个函数 |
| style | 新增 .search-bar, .search-nav, .search-highlight 等 CSS |
| import | 补充 Search, ArrowUp, ArrowDown 图标组件 |

## 任务2：段落名称显示

### 2.1 需求分析

当前段落头部只显示 #{{ para.index }} 和匹配类型标签（如 SPECIAL），缺少段落当前关联的样式规则名称（para.ruleName）。

#### 2.1.1 问题澄清

**问题1：当 ruleName 为空时如何显示？**

| 方案 | 描述 |
|------|------|
| A（推荐） | 不显示任何额外内容，保持原样 |
| B | 显示"未设置样式"灰色占位文字 |

推荐方案 A。避免大量未设置段落的冗余文字造成视觉噪音。

**问题2：ruleName 显示位置？**

| 方案 | 描述 |
|------|------|
| A（推荐） | 在匹配类型标签后方，作为靠左排列的文本 |
| B | 在序号和类型标签之间 |
| C | 放在 .adjust-preview 区域右侧 |

推荐方案 A。显示效果为：#0 SPECIAL 标题样式

**问题3：样式名称太长时如何处理？**

| 方案 | 描述 |
|------|------|
| A（推荐） | CSS 单行截断加省略号，配合 el-tooltip hover 查看完整名称 |
| B | 允许自动换行 |
| C | 截断但不加省略号 |

推荐方案 A。

### 2.2 技术方案

在 .adjust-header 的 el-tag 后添加：

```html
<el-tooltip v-if="para.ruleName" :content="para.ruleName" placement="top" :show-after="300">
  <span class="adjust-rulename">{{ para.ruleName }}</span>
</el-tooltip>
```

CSS：

```css
.adjust-rulename {
  font-size: 12px;
  color: #606266;
  max-width: 100px;
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
  flex-shrink: 1;
  min-width: 0;
}
```

### 2.3 改动范围

| 项目 | 内容 |
|------|------|
| template | 在 el-tag 后插入规则名称 span |
| style | 新增 .adjust-rulename CSS |

## 任务3：展开性能优化

### 3.1 需求分析

用户反馈点击段落展开内容时页面响应缓慢。

#### 3.1.1 性能瓶颈分析

**瓶颈1：el-collapse-transition 的 JS 驱动动画**

每次展开/折叠时，组件会通过 JavaScript 获取目标元素的实际高度，再从 0 动画到该高度（或反向）。这个测量过程会触发浏览器的强制重排（forced reflow）。

**瓶颈2：v-show 导致所有 DOM 节点常驻**

当前使用 v-show 控制展开状态，所有段落的 .adjust-body DOM（含 el-select、样式信息等）始终存在于 DOM 树中。当段落数量达 100+ 时，DOM 中包含 100+ 个 el-select 组件实例，每个都绑定完整的规则选项列表。

**瓶颈3：级联布局抖动**

展开一个段落会导致右侧面板高度变化，可能触发滚动条出现/消失，进而引发新一轮布局计算。

**主要瓶颈判定：DOM 节点数量过多 + 强制重排。** 次要瓶颈：响应式通知范围过大。

#### 3.1.2 问题澄清

**问题1：是否保留展开/折叠动画？**

| 方案 | 描述 | 评价 |
|------|------|------|
| A（推荐） | 保留 el-collapse-transition，但将 v-show 改为 v-if | 保持动画体验，减少折叠态 DOM 节点 |
| B | 完全去掉动画，仅用 v-if | 性能最佳但体验突兀 |
| C | 改用纯 CSS transition（max-height 方案） | 动画速度不均匀，需预估值 |

推荐方案 A。el-collapse-transition 同时支持 v-show 和 v-if。使用 v-if 时，折叠状态 DOM 被完全销毁，展开时重新创建并触发进入动画。虽然首次展开有创建开销，但用户通常只展开少量段落，总体体验更好。

**问题2：是否引入虚拟滚动？**

| 方案 | 描述 |
|------|------|
| A（推荐） | 暂不引入。先通过 v-if 优化，段落数 < 200 场景已足够 |
| B | 引入 vue-virtual-scroller | 复杂度高，段落展开态高度不固定难以处理 |

推荐方案 A。后续如果段落数超过 200 仍卡顿，再考虑虚拟滚动。

### 3.2 技术方案

#### 3.2.1 核心优化：v-show 改 v-if

```html
<!-- 改造前 -->
<el-collapse-transition>
  <div v-show="expandedAdjustItems[index]" class="adjust-body">...</div>
</el-collapse-transition>

<!-- 改造后 -->
<el-collapse-transition>
  <div v-if="expandedAdjustItems[index]" class="adjust-body">...</div>
</el-collapse-transition>
```

#### 3.2.2 辅助优化

(1) expandedAdjustItems 改用 shallowReactive 代替 reactive。因为值始终为 boolean 原始类型，无需深度追踪。

(2) 在 v-for 上添加 v-memo 指令，减少不必要的虚拟 DOM diff：

```html
<div v-for="(para, index) in parseResult.paragraphs"
     :key="index"
     v-memo="[para.ruleId, para.matchedType, expandedAdjustItems[index],
              hasSearched, searchResults.includes(index), currentMatchedIndex === index]">
```

注意：如果 v-memo 依赖数组过大导致反效果，可移除 v-memo，仅保留 v-if 优化。

#### 3.2.3 预期优化效果

| 指标 | 优化前（100 段落） | 优化后（100 段落） |
|------|------------------|------------------|
| DOM 节点数（全部折叠） | ~300+ | ~100+ |
| 展开一个段落耗时 | 200-500ms | ~50ms 以内 |
| 展开时的 Layout 次数 | 多次强制重排 | 1-2 次 |

### 3.3 改动范围

| 项目 | 内容 |
|------|------|
| template | v-show 改为 v-if（1 处），添加 v-memo（1 处） |
| script | reactive 改为 shallowReactive（第 194 行附近） |

## 跨任务影响分析

### 交互冲突

1. 搜索导航 + 段落展开：搜索定位时先设置 expandedAdjustItems[paraIdx] = true，然后 await nextTick() 等待 DOM 创建完成，再执行 scrollIntoView。如果使用 v-if（任务3），DOM 在折叠时被销毁，nextTick 确保创建完成后才滚动。

2. v-memo + 搜索状态变更：v-memo 的依赖数组必须包含 hasSearched 和 searchResults，否则搜索时段落不会重渲染高亮状态。

### 建议实施顺序

1. 任务2（段落名称显示）—— 改动最小，风险最低
2. 任务3（性能优化）—— 改动 DOM 结构，影响展开逻辑
3. 任务1（搜索功能）—— 依赖任务3的展开行为

### 总结

| 任务 | 核心改动 | 代码量 | 工作量 | 风险 |
|------|----------|--------|--------|------|
| 任务1：搜索功能 | 新增搜索栏和导航栏 | ~80 行 | 0.5-1 天 | 低 |
| 任务2：段落名称显示 | 增加 ruleName 显示 | ~10 行 | 0.2 天 | 极低 |
| 任务3：性能优化 | v-show 改 v-if，shallowReactive | ~5 行 | 0.3 天 | 中（需验证 el-collapse-transition 兼容性） |
